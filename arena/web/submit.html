Submit a system

Three submission modes, one evaluation path. There is no form on this page because there is no backend to accept one: a submission is a pull request or an issue, and it is evaluated by the Runner before anything appears on the leaderboard.

Manual submission No account, no upload, no tracking

What you are submitting

You are not submitting a score, and you cannot submit one. You are submitting a run request: a pinned description of a system, plus everything needed to execute it against a frozen Season inside the trusted runtime. The score is produced by the evaluation, not by the submitter, and there is no path by which a number you supply reaches the leaderboard.

Read this before you build anything

A system that cannot emit a ResearchArtifact envelope cannot be scored. The envelope is required rather than encouraged: one envelope, one validator, one place where "may this be published?" is decided. A system that returns prose instead cannot be validated, cannot be re-run against, and cannot be scored. Start from the envelope, not from the answer.

What every submission must produce任何提交都必须产出什么

Regardless of mode, the run must emit one artifact envelope containing all of the following. These are validation requirements, not documentation suggestions, and each one is checked by a validator that returns stable codes.

  • Sources declared, each pinned to a source-card snapshot hash with an identified licence.
  • Every claim scoped to a claim kind — mechanism, clinical, methodological, uncertainty or recommendation — with the evidence supporting it.
  • Every citation resolvable, and every supporting quote located in its source rather than paraphrased.
  • Every output file hashed, with a media type and a size.
  • All four version axes declared: runtime, skill, source, benchmark.
  • Limitations stated. At least one, in your own words, naming what the run does not show.

And one prohibition, stated separately because it is the failure this benchmark exists to make visible: a clinical efficacy claim may not rest on computational prediction alone. Docking, network inference and enrichment may support a mechanism claim. They may not support a claim about what happens in a patient. A run that states one is gated to the Experimental board with CLM004 / ART106, however strong the rest of its profile.

The evaluation flow

  1. Open an issue describing the system, its mode, its source repository or endpoint, its licence and its declared permissions. This is a conversation, not a queue position: most submissions are improved substantially at this step.
  2. Eligibility check. The declared permissions are reviewed against what the system actually needs, and the licence position is established. A submission that cannot name a licence for its sources is stopped here rather than after a run.
  3. Development-split run. The system is executed against the published development split so you can see where it fails before anything is frozen. Results at this stage are private to the submitter and the evaluators.
  4. Freeze the run request. Mode, image digest or endpoint, permission set, declared versions. After this point the request is immutable: changing it starts a new submission.
  5. Evaluation on the held-out split. Executed once, by the evaluators, under the Season's policy snapshot. The held-out labels are not available to the submitter at any point.
  6. Validation. The artifact envelope is checked by the pure-function validator. Every violation carries a stable code, and any hard-gate violation routes the run to the Experimental board rather than discarding it.
  7. Publication. The result bundle — scores, decomposition, trace, evidence, artifacts, claim verdicts — is written to the Frozen Benchmark Registry and appears on the leaderboard at the next data regeneration.
  8. Appeal window. A submitter may contest a scoring decision by opening an issue against the scorer, with the artifact and the case. An appeal can change a scorer or a Season; it cannot change a published row of a frozen Season. Corrections are issued as a new Season or an erratum, never as a silent edit.

There is no queue position, no fee, and no fast path. Two things move a submission forward: a system that resolves its citations, and a submission that declares what its system cannot do.

Codes you may get back

A refused claim or a failed validation is reported with a stable code, never as prose alone, because these strings end up in benchmark output and in paper tables and must not be renumbered by an edit. The run page prints the code next to its published meaning. The most common ones at submission time:

A refusal is fixable. CLM009 in particular is marked fixable by declaring the limit: the claim is permitted once the run states the extrapolation it is making. The point of the code is to tell you which of those two situations you are in — change your evidence, or change your sentence.

What will not be accepted

  • A number without an artifact. If the run cannot be re-executed, there is nothing to publish. A perfect score with no reproducible artifact is an anecdote with a decimal point.
  • Retrieval from undisclosed sources. Undeclared corpora cannot be licence-checked, cannot be snapshot-pinned, and cannot be cited.
  • Human-in-the-loop undisclosed. If a person contributed to an answer, the run request says so. A benchmark that measures a person and reports it as a system is measuring nothing useful.
  • Tuning against the held-out split. The development split exists so that this is unnecessary. Evaluation on the held-out split is run once; a resubmission that follows an attempt to infer the labels is declined.

What you get if it passes

A row on the trusted board with all eight dimensions decomposed, a run page with the full trace, and a citable composite version naming all four axes. If it fails a gate you still get the row and the run page — on the Experimental board, with the reason.

TCMScience Arena. A read-only evaluation surface. It renders published result bundles; it never computes a score, never re-ranks, and never writes a registry.

Static HTML, one stylesheet, one script. No server, no database, no cookies, no tracking.
